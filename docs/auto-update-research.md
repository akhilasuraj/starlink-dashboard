# In-app updates: Plezy research and Electron adaptation

Investigated 2026-09-28. Plezy source revision: `eda95bfbecb677b617efaf13b5ed8480ecb4edf3`. Electron updater source revision: `bed3a9c421a8a05c49f36a2af5d7ae3598cb1b95` (`electron-updater@6.8.9`); builder revision: `512a57ec9bcda593d3e0970bd2b9a33a63beeb57` (`electron-builder@26.15.3`). ## What Plezy does

Plezy is Flutter. Its release builds enable an update-check flag. Installed Windows copies delegate to WinSparkle through `auto_updater`; eligible macOS copies use Sparkle. Windows installation detection uses the Inno Setup uninstaller, with a separate marker excluding WinGet copies from the native path. Store/MSIX installations expose no in-app update action. Other eligible installs use a GitHub release check and browser-link dialog. The fallback records a six-hour check cooldown and skipped version; manual checks distinguish failures from no update. [Update service](https://github.com/edde746/plezy/blob/eda95bfbecb677b617efaf13b5ed8480ecb4edf3/lib/services/update_service.dart), [fallback dialog](https://github.com/edde746/plezy/blob/eda95bfbecb677b617efaf13b5ed8480ecb4edf3/lib/utils/update_dialog.dart).

The updater dependency is the author's fork pinned to `9e150f7`, rather than an unpinned package. [Dependency declaration](https://github.com/edde746/plezy/blob/eda95bfbecb677b617efaf13b5ed8480ecb4edf3/pubspec.yaml#L69-L73).

The build workflow signs the Windows installer with EdDSA when the signing secret exists. It generates an RSS appcast containing platform-specific installer URLs, sizes, version/build numbers, signatures and Windows installer arguments. An enclosure is omitted when its signature is absent. [Build workflow](https://github.com/edde746/plezy/blob/eda95bfbecb677b617efaf13b5ed8480ecb4edf3/.github/workflows/build.yml#L594-L615), [appcast generation](https://github.com/edde746/plezy/blob/eda95bfbecb677b617efaf13b5ed8480ecb4edf3/.github/workflows/build.yml#L986-L1054).

After release publication, another workflow copies that release's appcast to an `appcast` branch. The app reads this branch through jsDelivr. This separates the small discovery feed from the installer assets in GitHub Releases. [Feed publication](https://github.com/edde746/plezy/blob/eda95bfbecb677b617efaf13b5ed8480ecb4edf3/.github/workflows/update-packages.yml#L115-L141), [feed URL](https://github.com/edde746/plezy/blob/eda95bfbecb677b617efaf13b5ed8480ecb4edf3/lib/services/update_service.dart#L17-L19).

## Adaptation for Starlink Dashboard

Use the existing Electron/NSIS packaging with `electron-updater`, which supports GitHub Releases, progress reporting and generated update metadata. Configure the public owner/repository in builder `publish`; builder then embeds `resources/app-update.yml`. Use the updater package, not Electron's built-in Squirrel updater. No Flutter dependency, appcast branch or additional CDN is needed. [Official stable-version setup](https://www.electron.build/v26/docs/features/auto-update/).

Publish the tested NSIS installer, generated `latest.yml`, and corresponding `.exe.blockmap` together. `latest.yml` must describe the exact version, filename, size and SHA-512 of the installer tested by the release gate. Blockmaps support differential downloads; missing maps can fall back to the full installer. Prepare all assets in a draft release before publishing it. This is our recommended workflow boundary. [Differential-download implementation](https://github.com/electron-userland/electron-builder/blob/bed3a9c421a8a05c49f36a2af5d7ae3598cb1b95/packages/electron-updater/src/AppUpdater.ts#L801-L889), [NSIS download implementation](https://github.com/electron-userland/electron-builder/blob/bed3a9c421a8a05c49f36a2af5d7ae3598cb1b95/packages/electron-updater/src/NsisUpdater.ts#L42-L105).

Current Starlink releases use stable-semver tags such as `v1.2.0` but are marked GitHub prereleases. In 6.8.9, explicitly enabling `allowPrerelease` with a stable current version and no explicit channel selects the first Atom-feed release; a stable-semver tag resolves to `latest.yml`. Default stable-only discovery excludes GitHub prereleases. Keep `allowDowngrade=false` and publish versions monotonically: the provider chooses feed order, not maximum semver. Explain prerelease inclusion in the UI. [Exact GitHub provider](https://github.com/electron-userland/electron-builder/blob/bed3a9c421a8a05c49f36a2af5d7ae3598cb1b95/packages/electron-updater/src/providers/GitHubProvider.ts#L55-L176).

Recommended interaction: automatic discovery, explicit **Download update**, progress/error/retry state, then **Restart and install**. Set `autoDownload=false` and `autoInstallOnAppQuit=false`; ordinary tray quits and Windows logoff must not unexpectedly start installation. Keep updater actions in the main process behind the existing validated preload/IPC boundary; the renderer receives plain status, not arbitrary feed URLs or executable paths. [Stable API options](https://www.electron.build/v26/docs/api/electron-updater.class.appupdater/).

## Collector shutdown is a prerequisite

In 6.8.9, `quitAndInstall()` calls `install()` first; NSIS launches the installer before scheduling Electron's quit. An asynchronous `before-quit` collector handler alone is therefore too late. Our implementation must request orderly shutdown, stop collector restart/status timers, wait for the owned collector's `close`, and only then invoke `quitAndInstall`. Preserve forced-shutdown handling and test the absence of an installer launch before confirmed child exit. Do not install during OS session ending. [Updater ordering](https://github.com/electron-userland/electron-builder/blob/bed3a9c421a8a05c49f36a2af5d7ae3598cb1b95/packages/electron-updater/src/BaseUpdater.ts#L15-L27), [installer launch](https://github.com/electron-userland/electron-builder/blob/bed3a9c421a8a05c49f36a2af5d7ae3598cb1b95/packages/electron-updater/src/NsisUpdater.ts#L125-L178).

## Trust and rollout limits

The existing Windows build is unsigned. Download SHA-512 validation detects corrupted bytes against metadata; it does not authenticate the publisher if an attacker can replace both metadata and installer. NSIS updater signature verification returns success without a configured publisher name, so this first implementation relies on HTTPS and GitHub repository/release permissions. Do not describe it as having Plezy's EdDSA authenticity guarantee. Authenticode signing plus enforced publisher identity is a future improvement. [Hash parameters](https://github.com/electron-userland/electron-builder/blob/bed3a9c421a8a05c49f36a2af5d7ae3598cb1b95/packages/electron-updater/src/AppUpdater.ts#L708-L716), [signature behavior](https://github.com/electron-userland/electron-builder/blob/bed3a9c421a8a05c49f36a2af5d7ae3598cb1b95/packages/electron-updater/src/NsisUpdater.ts#L109-L123).

The current documentation site's root describes **unreleased v27**. Its built-in Ed25519 signed-manifest feature must not be assumed available in the selected stable 6.8.9 updater / 26.15.3 builder. [Version notice and signed-manifest design](https://www.electron.build/docs/features/signed-update-manifests/).

Already installed 1.2.0 copies have no updater and require one manual bootstrap installation. Thereafter, complete update verification needs two installed versions: discover/download a newer package, restart/install, confirm the new version starts and history/preferences survive. Mock state-machine tests cannot establish this installer transition.
