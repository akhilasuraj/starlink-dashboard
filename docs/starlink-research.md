# Starlink desktop dashboard: interface and tooling research

Research date: 2026-09-27. Scope: a desktop app for one Starlink user, with monitoring and history as the first priorities. This is a source review, not a live test against a dish or router.

## The interface boundary that determines the product

| Interface | What it can provide | Access and stability |
| --- | --- | --- |
| **SpaceX's supported local Device API** | `GetDiagnostics` for dish and Starlink router: identity, software/hardware versions, dish alerts, disablement, alignment, stow state, and router network/client counts. The published protobuf defines the supported fields. | SpaceX calls this its "officially supported local API." Dish: `192.168.100.1:9200`; router default: `192.168.1.1:9000`. Dish firmware must be newer than `2023.51.0`, router firmware newer than `2023.55`; earlier devices may return `UNIMPLEMENTED`. [SpaceX README](https://github.com/SpaceExplorationTechnologies/enterprise-api/blob/master/device-api/README.md), [SpaceX protobuf](https://github.com/SpaceExplorationTechnologies/enterprise-api/blob/master/device-api/device.proto). |
| **Richer local gRPC calls used by community projects** | Live throughput, PoP latency/drop, outage and history samples, obstruction maps, and some controls. The `starlink-grpc-tools` author documents that Statistics-page data mainly comes from `get_history`, while status data resembles app Debug Data. | These calls are outside the narrow published `GetDiagnostics` protobuf, so treat them as firmware-dependent. The project has needed fixes for firmware changes, including its 2025 and 2026 releases. [Toolkit README](https://github.com/sparky8512/starlink-grpc-tools/blob/main/README.md), [releases](https://github.com/sparky8512/starlink-grpc-tools/releases), [SpaceX protobuf](https://github.com/SpaceExplorationTechnologies/enterprise-api/blob/master/device-api/device.proto). |
| **Starlink enterprise cloud APIs** | Remote account management and near-real-time device telemetry. | Starlink says its Telemetry API is only for Premium Business and Enterprise customers, and access to the Management and Telemetry APIs is through an enterprise account manager. It is not a residential fallback. [Telemetry support](https://starlink.com/support/article/90109cc2-c7ec-31ff-d160-0a87f16ef759), [enterprise tools](https://starlink.com/support/article/2a140927-d1e3-de25-9a73-71e1410a76e9). |

The practical recommendation is a **local-first adapter with capability detection**. Use supported diagnostics as the durable baseline; offer richer local metrics when the device actually answers those community calls. Represent unsupported or absent fields as unavailable, never as zero. The interface distinction follows directly from comparing [SpaceX's published protobuf](https://github.com/SpaceExplorationTechnologies/enterprise-api/blob/master/device-api/device.proto) with the [community toolkit's status/history calls](https://github.com/sparky8512/starlink-grpc-tools/blob/main/starlink_grpc.py).

## Features and data semantics

- Starlink describes its app Statistics page as showing speed, uptime, latency, outages, and alerts. These are strong targets for a desktop monitoring view. [Starlink support](https://starlink.com/support/article/8d137188-3031-ab18-7789-edad95f1bb22).
- Throughput samples from the dish are **traffic currently flowing**, not a measured connection capacity. Starlink's separate Speed Test checks router-to-internet by default, and its advanced test distinguishes device-to-internet from device-to-router. Label these separately in the UI. [Starlink speed-test guide](https://starlink.com/support/article/a72d6157-210d-d5f4-76d8-27c932dc4457), [community history field definitions](https://github.com/sparky8512/starlink-grpc-tools/blob/main/starlink_grpc.py).
- For history, the toolkit says firmware reduced the dish's returned history to about **15 minutes of one-second samples**. A desktop app needs its own time-series storage if it promises days or months of history. Poll at an interval comfortably below 900 seconds, record sample timestamps/counters, and deduplicate overlapping history after reconnect. The storage design is an inference from the documented ring-buffer behavior. [Toolkit README](https://github.com/sparky8512/starlink-grpc-tools/blob/main/README.md).
- Obstruction visualizations are feasible through the community call; `dish_obstruction_map.py` already renders it. The mobile app's camera-based **Check for Obstructions** installation scan requires phone camera/sensors and should not be represented as a dish telemetry feature on desktop. [Toolkit README](https://github.com/sparky8512/starlink-grpc-tools/blob/main/README.md), [Starlink troubleshooting](https://starlink.com/support/article/615d298c-24a7-7e3c-3fd7-9aa96476eac7).
- `gps_sats` in community telemetry describes GPS/GNSS reception, not a count of Starlink satellites currently serving the dish. The app should rename the current project's "GPS satellite tracking" claim accordingly and avoid drawing a live serving-satellite map from that value. This is an inference from the field and its context in the [toolkit implementation](https://github.com/sparky8512/starlink-grpc-tools/blob/main/starlink_grpc.py).
- Local dish **location coordinates** are a fragile feature: the toolkit now warns that since May 2026 they are unavailable via gRPC for most service plans, despite older instructions for enabling LAN location. SpaceX's supported diagnostic protobuf includes a location message with an `enabled` flag, so show it only after an actual successful read. [Toolkit README](https://github.com/sparky8512/starlink-grpc-tools/blob/main/README.md), [SpaceX protobuf](https://github.com/SpaceExplorationTechnologies/enterprise-api/blob/master/device-api/device.proto).
- With a third-party router or bypass mode, Starlink says a static route to `192.168.100.1` may be needed. The app should report dish unreachable and offer route guidance instead of interpreting it as a service outage. [Starlink enterprise dashboard help](https://starlink.com/support/article/6aff51c6-254a-700e-c175-4c05a2b8c894), [Home Assistant Starlink integration](https://www.home-assistant.io/integrations/starlink).

[Changelog](https://github.com/clarkzjw/starlink-grpc-golang/blob/master/CHANGELOG.md). |

**Dependency identity correction for this repository:** `requirements.txt` installs [`starlink-client`](https://pypi.org/project/starlink-client/) by Hector Oliveros and `backend/server.py` imports `starlink_client.grpc_client`. The README credits `sparky8512/starlink-grpc-tools`, which is a different project/package. PyPI lists `starlink-client` as requiring Python **>=3.9**, so the README's Python 3.7 promise is inconsistent with its actual dependency. PyPI's description also includes remote calls based on manually copied browser cookies; avoid adding that path for a personal local monitor. [PyPI package and author/requirements](https://pypi.org/project/starlink-client/), [sparky8512 core package](https://pypi.org/project/starlink-grpc-core/).

## Desktop architecture options

1. **Incremental recovery, fastest to validate:** keep Electron, replace the backend's gRPC call layer with a small interface that tries SpaceX diagnostics and `starlink-grpc-core` status/history, persist readings to SQLite, and make each chart explicitly distinguish current traffic from speed test results. Bundle a supported Python runtime rather than requiring users to install Python separately; Python documents an embeddable Windows distribution suitable for inclusion in applications. Maintain Electron's current-version, context-isolation, sandbox, and narrow IPC practices. [Python Windows documentation](https://docs.python.org/3/using/windows.html), [Electron security](https://www.electronjs.org/docs/latest/tutorial/security), [core package](https://pypi.org/project/starlink-grpc-core/).
2. **Product rebuild after validating device data:** Tauri 2 with a web UI and Rust (or an intentionally bundled sidecar) can use the Windows WebView2 runtime, avoiding a separately bundled browser engine. It requires Rust and Microsoft C++ build tools for development. This is attractive for smaller installers and a single desktop process, but rewriting the collector is more work than the monitoring problem currently justifies. [Tauri overview](https://tauri.app/start/), [Windows prerequisites](https://tauri.app/start/prerequisites/).
3. **Monitoring appliance / multi-device future:** use the existing Prometheus/MQTT/Influx exporters or Home Assistant integration and build a web dashboard against that store. This suits an always-on machine or fleet, while a standalone tray app is simpler for one Windows user. [Toolkit exporters](https://github.com/sparky8512/starlink-grpc-tools/blob/main/README.md), [Home Assistant integration](https://www.home-assistant.io/integrations/starlink).

Suggested first implementation slice: probe dish and optional Starlink router; show capabilities and firmware; collect supported diagnostics and community status/history with timeouts; store minute/hour/day rollups in SQLite; render truthful uptime, outages, latency/drop and traffic charts; then add obstruction and alerts. Keep write controls (reboot/stow/Wi-Fi changes) out of the first slice because monitoring/history is the stated priority and the supported published proto only defines `GetDiagnostics`. [SpaceX protobuf](https://github.com/SpaceExplorationTechnologies/enterprise-api/blob/master/device-api/device.proto), [toolkit README](https://github.com/sparky8512/starlink-grpc-tools/blob/main/README.md).

## What still needs hardware validation

Test on the user's actual dish generation, firmware, service plan, router/bypass configuration, and Windows network. Confirm which RPCs return data, which fields are absent, whether the official diagnostics endpoint works, the true history span, and how the app behaves during reboot/outage. Published protocol definitions and community tools establish plausible capabilities; they cannot establish availability on this particular installation. [SpaceX version requirements](https://github.com/SpaceExplorationTechnologies/enterprise-api/blob/master/device-api/README.md), [community firmware release notes](https://github.com/sparky8512/starlink-grpc-tools/releases).
